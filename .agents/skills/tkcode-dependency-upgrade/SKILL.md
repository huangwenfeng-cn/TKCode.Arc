# 依赖升级与主分支同步

先读 [明文规范](../../AGENTS.md) 和 [实施指南](../../implementation-guide.md) 第 3、13、15 节。

1. 从用户请求区分只评估、实施升级或同步 main。只评估时保持版本和源码不变；已明确授权实施时完成必要分析后继续，不重复索要批准。
2. 读取工作区状态，记录原版本/提交和目标版本/提交。版本来源核对 `global.json`、`build/Versions.props`、`Directory.Packages.props` 及相关 csproj。
3. 检查完整变更文件清单，再定位可影响本项目的 API、行为、主题、资源、绑定、程序集、依赖、目标框架、MSBuild 和平台变化。
4. 对行为判断引用确切 diff、公开契约或可复现验证。发布说明用于定位线索，编译通过不证明行为或二进制兼容。
5. 需要依赖资料时使用准确版本的公开文档或允许的上游来源，临时检出放仓库外。核心 clean room 规则继续有效；AtomUI 实现源码不作为依赖适配依据。
6. 列出本项目消费者、直接与间接影响、所需兼容修改、Gallery 注册/演示/API 翻译影响和定向验证。
7. 采用已授权的合并方式。默认保留历史，不自行 rebase 已推送分支，不用强推或硬重置清理冲突。
8. 依赖变动后构建完整依赖，再核对测试、Desktop 和截图宿主的程序集一致性。运行与实际变化对应的回归，不自动跑所有平台。
9. 整理重复 Unreleased、迁移说明和实施指南。上游有意破坏已发布契约时明确记录与本地规则的冲突，不把它变成新组件豁免。

遇到新发现时完成授权范围内可独立推进的工作；只有缺少必要决策、凭据或涉及未授权不可逆动作才询问用户。

是否提交、推送、打标签或发布分别依据用户授权，并读取同级 `tkcode-git-delivery`。没有实际验证的框架、平台和发布模式必须保持未验证状态。
